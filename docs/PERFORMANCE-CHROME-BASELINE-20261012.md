# Chrome 小规模卡顿检查点

## 验收范围

按用户最新确认，以 **10 张卡**作为基础验收；1 张、4 张卡用于复现。基础规模的操作、编辑、同步和首次加载达标前，暂停扩大到 30 张、100 张及以上。历史大规模记录保留，不作为基础规模要求。

没有接管用户当前已登录的 Chrome。测试使用本机安装的 Chrome 154.0.8037.98、独立临时环境和 1440 × 960 视口。当前自动采样为后台浏览器运行，能测页面计算、布局、浏览器输入等待和实际网络；不能替代用户已有本地数据、真实 QQ 授权、真实房间及实际显示设备的验收。3D 骰子的硬件演出另行验证。

285 批次已发布，见 [发布记录](PERFORMANCE-CLOSEOUT-PUBLICATION-285.md)。本检查点中的第二批修改尚未部署，不能把候选数据写成线上改善。

## 计时与候选修改

旧计时从点击进入处理函数才开始，遗漏输入队列等待。当前从浏览器创建可信指针按下事件开始，分别记录输入等待、框架可见、内容就绪及长任务，并附加浏览器 Event Timing。250 ms 人为阻塞校准记录到约 248 ms 等待，见 `input-timing-calibration.json`。定义参照 [W3C Event Timing](https://www.w3.org/TR/event-timing/)。自动化定位和等待控件可点击的时间仍不属于该浏览器事件计时。

第二批候选包含以下修改：

- 大资料按小批返回页面；第三方资料及索引的内容哈希转移到后台，同时保留原始缓存与修订身份。
- 资料、进度和来源名称更新采用较低优先级，给用户操作让出处理机会。
- 虚拟列表避免在 React 状态计算及首次重置时重复强制读取页面尺寸。
- 公告先显示与原弹窗一致的加载框架；更新日志在首次查看时建立内容。公告确认规则、FAQ、更新日志及赞助内容继续保留。

单纯拆分后台返回没有明显缩短整体耗时，后续判断以组合修改和匹配条件的对照为准。公告更新日志延后创建本身也未解决首次反馈延迟；即时反馈改善来自可见的加载框架。

正常生产构建仍因消费者源码改变而要求新的完整规则回放。当前本机诊断构建使用单独入口和冻结源码的报告，不认证实验消费者，标记 `DIAGNOSTIC-ONLY.json`、`publishable=false`。没有修改正式保护检查，也不能用这个包发布。最终源码的完整回放、正式构建和精确提交 CI 完成前不得部署。
