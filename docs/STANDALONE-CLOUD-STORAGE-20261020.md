# 本机存储初始化与保留数据的恢复

范围仅为独立 `/cloud-lab/` 前端。正式站、枭熊、后台数据库和 QQ 会话不在发布范围。

## 原因与修复

原 `cloud/sync.ts`、`cloud/bindings.ts` 用 `openDB(name,1)` 直接读取，缺少初始化回调；若先于角色簿打开，会创建没有 `documents`／`cache` 存储区的版本 1 空库。后来角色簿同样打开版本 1，不再触发 upgrade，因此抛出 NotFoundError。两个“云端先开库”的定向用例在原实现均失败，修复后通过。这证明了一个实际代码缺陷，不能据此断言它是浏览器内一切存储异常的唯一原因。

所有角色簿、缓存及云端回执读写共用完整结构初始化。既有库按实际版本打开，仅添加缺失存储区；不删除、清空、替换既有存储区或记录。版本切换关闭旧连接，失败连接可重试。其他旧标签占用升级时给出可操作的错误，保留原记录。

如果旧库缺失的是角色正文区，结构修好后仍要求显式恢复备份，阻止新建空角色的自动保存。测试页提供从完整 JSON 恢复角色簿的入口：先验证全部角色，再用单一事务落盘；保留 ID、修订、数值、条目、填写内容及规则包；已有工作区则拒绝覆盖。普通“导入为新副本”的行为不变。

恢复后，玩家在本人已登录卡库重新选择原卡，才可恢复云端连接。核对账号与权限、既有待定回执和完整内容散列；个人内容不同即拒绝，不覆盖任何一端。标准备份包含站点共享来源视图，因此只在显示结果完全相同的情况下重建共享来源与角色原始来源的分离，保留站点设置及个人规则。已有冲突或未确认同步不能被恢复流程抹掉。

重建后的来源分离先持久化成功，再启用云端回执。保存失败或关闭页面不能留下指向尚未保存导出视图的同步绑定；等待保存期间的后续人物编辑保留。

## 本人实卡公网验收

在用户已登录的 Codex 内置浏览器实际操作。先从原失败页面完整导出两卡备份，与上一份私有备份的全部角色字段一致，再关闭旧页面以释放存储连接。新版显示“本机存储结构已修复”，停在恢复入口；通过真实文件选择器恢复原始 JSON，显示“已保存到本机”。刷新后两张原卡及身份仍在，QQ 会话仍有效。由本人私人卡库重新选择原卡后仍只有两张标签，没有重复角色。

1280×720、页面可见、保留原 A4 卡面与样式，实际点击上方两个原始标签共 3 组往返（6 次）。页面自身埋点记录如下，工具调用等待不计入：

| 路径 | 布局提交 | 双 RAF 绘制观测 |
| --- | --- | --- |
| 返回本机卡 | 26.2–43.6 ms | 55.6–89.8 ms |
| 返回本人云端卡 | 49.9–74.4 ms | 84.0–129.1 ms |

真实云端卡生命 1→2，提交 63.3 ms、绘制观测 74.6 ms，已有同步事务 268.9 ms；保存调度本身另有约 650 ms 合并等待，不能把事务数值当作从输入到保存的全程。服务器只读核验原修订 20→21、生命 2。切走再切回仍是 2，刷新后仍为 2，本机／云端均已保存，无错误。

再经页面输入将生命恢复到 1，提交 64.0 ms、绘制观测 75.9 ms、同步事务 194.4 ms；服务器修订 22，排除修订／更新时间后的完整原卡内容散列与测试前相同，临时生命仍为 0。服务器总卡数 141，其他 140 张卡内容散列不变。未通过数据库写入模拟保存或还原。

随后经正式导出界面再次生成完整两卡 JSON。两张角色身份、人物填写、条目、数值逐项一致；仅目标卡的修订／更新时间，以及正常程序维护的站点公共来源清单不同。公共自动默认来源由 190 补齐为 371，旧启用来源全部保留，手动增加／排除选择不变；此项站点视图维护没有写回云端原始来源。私有导出、真实服务器正文及测试探针均未进入 Git／源码归档／发布包。

真实页面保留打开，最终原值截图及逐项结果存于忽略的 `.local-evidence/cloud-stage2/`。本次是当前内置浏览器、两张实际原卡的实测，不能推广为所有设备／大型卡册／QQ 与微信内置浏览器均已验收，也不承诺 1 ms 切换。
