数值计算与运行资源分开：护甲/武器求值不写角色；赠送法术由明确的来源同步维护。资源只在首次获得时初始化，刷新/停用/方案切换不补次数。等级下降导致特性实例重建时，按根来源和授予路径保留已用次数。独立学会的同名法术不合并、不连带删除。

缺少资料、身份歧义、未知公式和未支持形状会在自动化设置中显示。未支持不等于效果为零或整条规则已完成。当前代码只读结构字段，不执行上游脚本，不根据职业/特性显示名分支。

1. 资源与施法动作：本机共享池、明确选择次数/法术位、升环和事务回执已接入。继续绑定职业资源、动态次数上限、批量长短休恢复。仅在结构化 known/prepared 授权时提供额外法术位路径，正文未明确转成字段的资格不猜测。
2. 自选赠送与扩展法表：保存玩家选择，候选过滤和来源引用；卡面提示缺项、由玩家拖入，保留当前自由手动模式，不做强制向导。
3. 常驻修饰机制：迁移已复核的声明式 modifier 核心，补自然护甲/特殊方案、条件属性替换、豁免/抗性/移动、堆叠与冲突说明；人工覆盖优先级不变。
4. 职业成长与兼职：职业等级和总等级分域，进阶表、职业特性、自选资源上限；撤回与恢复不重复赠送。
5. 效果与战斗：持续时间、专注、触发/反应窗口、目标、暴击和伤害段、抗性/免疫/易伤、治疗与临时生命。
6. 多人权威与性能：确认的操作 ID、并发/重试/断线回执、持久数据与棋子投影一致性，以及真实多客户端验收。自动化本机通过不解决此前枭熊状态残留的线上问题。

每阶段都用机制覆盖多个条目；特例只作为声明式适配包。继续保留版本、来源、解释、人工接管、撤销及未知规则报告，避免把上万条内容变成上万个按名称匹配的函数。


## 次数数据的歧义与操作保证

2026-09-28 第二阶段校验发现：真实 Mark of Handling 数据使用 `daily: {"1": [多个法术]}`，但正文明确是每个法术各一次。不能把缺少 `e` 的多项列表无条件解释成共享。运行逻辑没有按这项专长名称特判；同类形状统一提示玩家选择“各自次数 / 共用次数”，尚未选择就不自动赠送该组。明确 `e` 仍按各自次数处理。

次数归属切换保守保留既有消耗，可能需要玩家在核对后手工修正余量；不通过切换得到新次数。共同计数器只建一份，晚加载其他成员也不补充。原计数记录保留用于恢复，但不再在快捷栏展示不属于当前方案的计数器。

消费请求携带操作 ID、动作序号、人物修订和所选付费方式。同一请求重放不再次扣费，旧序号或旧修订拒绝；免费次数耗尽不会自动选择法术位。只在全部校验通过后同步修改资源、法术位已用数和回执，由既有角色保存/撤销一起提交。该保证范围是本机同步事务，尚不是多人服务端交付保证。

上游依据：[additionalSpells 格式定义](https://raw.githubusercontent.com/TheGiddyLimit/5etools-utils/master/schema-template/util-additionalspells.json)。其中 daily 指长休，rest 指短休或长休；次数列表归属在部分真实数据中仍需要人工确认。不能因 JSON 通过 schema 就认定正文语义完全一致。
