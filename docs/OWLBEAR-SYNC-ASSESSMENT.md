# 角色卡网页与 Owlbear 双向同步评估

2026-09-21 更新：已新增独立的无额外云端同步服务器原型，见 [原型说明](../prototype/README.md)。在同一浏览器中由插件打开独立角色卡窗口，通过 postMessage 与常驻后台通信。生命值双向同步已通过浏览器模拟和 SDK 适配模拟测试，未进行真实房间验收；用户决定自行实测。未修改正式 Full Suite、推送或部署。下文的服务端方案保留为跨设备、长期存档等更大范围的设计，不是本次原型的必要依赖。

额外窗口投骰可沿同一桥接方向扩展：本地权威 Full Suite 的 `src/modules/dice/index.ts` 已有 `com.obr-suite/dice-quick-roll` 请求入口和 `com.obr-suite/dice-roll` 结果通道。正式接入宜由 Full Suite 自身接收桥接请求、执行其现有投骰流程，并关联请求与结果回传窗口，避免两端各掷一次。当前独立生命值原型没有接入投骰；也没有验证不同扩展之间的广播可见性，不能把已有通道当作已接通的跨扩展 API。

## 结论与玩家流程

可实现玩家同时打开一个 Owlbear 房间网页和一个独立角色卡网页，双方修改角色字段后同步。建议在现有 Full Suite 的常驻 background 中增加同步模块，双方连接自有 HTTPS/WSS 服务。可复用 obr.dnd.center 所在服务器，但是否复用旧角色卡后端进程需取得其当前源码并确认鉴权、数据库和部署情况。

玩家在角色网页启用同步；DM 在枭熊绑定对应棋子并批准角色权限；一次性配对后，下次分别打开两个页面即可重连。账号或角色访问凭证由自己的服务签发，不能把前端上传的 Owlbear playerId / GM 身份当作服务端已认证身份。界面只需显示已连接、待同步、冲突或场景离线状态。

```mermaid
flowchart LR
  W[独立角色卡网页] <-->|HTTPS / WSS| S[同步服务与角色记录]
  S <-->|WSS| B[Full Suite 后台同步模块]
  B <-->|Owlbear SDK| O[枭熊角色卡与已绑定棋子]
```

后台插件仍须在至少一个有权限且保持连接的房间客户端中运行。自己的服务器不能凭房间地址直接操作 Owlbear 场景。关闭所有房间客户端后，角色文档可继续云端编辑，场景同步显示待处理；重连要核对版本，不把旧场景值自动覆盖新文档。浏览器休眠也按断线处理。

## 已检查的工程事实

枭熊权威目录为 `U:/枭熊插件/obr-suite`，工作树有大量既有修改，仅只读检查。网站目录为 `D:/Desktop/DND-card-web`。

| 枭熊 `utils/statEdit.ts:88` | 通过 SDK 修改棋子当前 HP / 临时 HP / 上限 / AC，兼容旧气泡字段 | 同步操作入口、并发控制、服务端回执 |

代码已发现的实际兼容差异：网页目前导出 `inventory.coins`，枭熊完整卡读取 `inventory.currency.wallet`（fullscreen-page.tsx:1884）；插件绑定读取 `auto_resources`，网页目前导出 `web_resources`。因此“schema_version 都是 0.3”不能作为互操作正确的证明。转换适配器要用插件真实夹具验证，不能只用网页自身导出再自身导入的往返测试。

`panel-page.ts:50` 明确记录旧 data.json 为前端软隐藏、未实现服务端访问控制；当前 PUT 调用也未携带应用授权头。此为客户端代码证据，不等于已经审计了线上后端或网关。联网同步之前应核查并补齐独立的服务器读写授权，不能仅凭知道 roomId / cardId 就允许写入。

只读取了公开 manifest：稳定地址返回 1.3.5；本次读取 suite-dev 地址却返回 1.3.4 和 `/suite/background.html`，与本地 dev 1.0.158-dev 不同。未据此推断线上 bundle 内容。实施时须重新核对测试安装地址、实际构建与缓存，在独立测试房间联调。

## 同步哪些数据

| 数据 | 建议行为 |
| --- | --- |
| 当前生命、临时生命、法术位消耗、特性资源、激励、死亡豁免、条件状态 | 双向；各字段接入真实编辑入口；条件保留稳定 ID、来源和层数 |
| 职业、等级、属性、技能熟练、专长、法术库与预备列表 | 原生角色文档保留完整结构；枭熊支持的编辑映射为明确操作，不以简化 JSON 重建整张网页卡 |
| AC、先攻、速度、生命上限 | 网页计算并发送结果；枭熊手动改结果时保存带来源的调整 / 覆盖，不改写基础属性凑结果，也不在两端循环重算 |
| 背包数量、装备、同调、货币 | 双向；条目使用稳定实例 ID，区分同名物品和不同来源 |
| 头像 | 独立图片资源上传，消息只带引用与裁剪设置；不把 base64 图塞进每次状态同步 |
| 配色、纸面布局、折叠、资料滚动 | 默认留在网页；可随私有角色文档保存，不写进棋子元数据 |
| 棋子位置、地图缩放、灯光、迷雾、装饰附件 | 属于场景，不属于角色属性；不触发整卡同步 |

只同步明确的角色字段。普通移动棋子不能导致全量角色保存。官方 items.onChange 返回整个场景条目集合，后台应维护绑定索引及字段签名，仅提取有关棋子的实质变化。

角色文档 ID 与棋子 ID 分开：一个人物可以跨场景使用。同一场景出现分身 / 变身 / 复制棋子时，明确哪个是运行状态的主实例；复制棋子不能自动成为另一名玩家的同步授权。场景切换使用绑定代次，旧异步结果不得写入新场景。

## 主方案与并发约束

服务保存网页完整文档与可供枭熊读取的兼容投影。网页不对每次变更重复 export / import。所有操作带 characterId、bindingId、operationId、基础修订号及变更字段；服务验权、去重并按角色顺序提交，返回新修订和确认。

不同字段可以合并；同一字段的过期绝对值写入需拒绝或让用户选择。扣血 / 消耗发送有语义的增减操作：例如 HP 20 时同时 -5 与 -3 应得到 12，不能由最后到达的 17 或 15 覆盖；伤害如何消耗临时 HP 仍由明确操作定义，不从任意文本猜测。重复重连不能再扣一次。

同一绑定只能有一个持有效租约的场景写入桥接器。优先 DM，允许授权的拥有者在具备实际棋子权限时承担；切换桥接器必须 fencing / 代次验证，阻止旧连接继续写。服务已保存不等于场景已成功写入，UI 分开显示持久化与场景应用回执。

要保证双方同时修改不丢失，必须让 Full Suite 的 HP / 状态 / 资源写入入口经过同一操作协调路径，不能仅增加一个 onChange 监听器。纯监听能发现“已经变成什么”，无法恢复两个旧版客户端同时覆盖时丢掉的操作；第三方插件直接改 metadata 也不保证无损并发，只能适配其可观测结果并处理冲突。

回显使用 operationId / 修订号和字段签名去重，不能把自己的场景写入再次当新操作上传。断线仅排队明确操作；重连核对服务修订、绑定代次和目标权限，再补发。规则更新与角色升级不得刷新掉当前 HP 或已消耗资源。撤销同步为一次受校验的新操作，不能回退整个旧快照抹掉别人刚做的修改。

## 为什么不首选纯浏览器互通

- `BroadcastChannel` 受同源及顶层站点的存储分区限制。独立角色网页与嵌在 owlbear.rodeo 的 iframe 即使托管在同域，也不应假定能互通。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API)
- `postMessage` 可以用于插件打开的角色窗口，前提是保留窗口引用并校验 origin / source；需在真实 Owlbear 中确认沙箱、弹窗、刷新与重新打开后的行为。可以做无需新后端的受限版本，但不适合任意独立打开两网页、跨设备及云端恢复的主需求。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)
- `OBR.broadcast` 是房间内临时消息通道，单消息 16 KB；不是任意外部网页可访问的持久消息服务。[官方文档](https://docs.owlbear.rodeo/extensions/apis/broadcast/)
- 房间 metadata 总量上限 16 KB，只适合小型配置和引用；完整人物、长规则正文和头像放自有存储。[官方文档](https://docs.owlbear.rodeo/extensions/apis/room/)

官方支持通过扩展 iframe / background 使用 SDK，读写和监听场景条目，因此房间侧桥接有明确公开 API 可用：[扩展架构](https://docs.owlbear.rodeo/extensions/getting-started/)、[Items](https://docs.owlbear.rodeo/extensions/apis/scene/items/)、[Manifest](https://docs.owlbear.rodeo/extensions/reference/manifest/)。WebSocket 作为双方连接自有服务的长连接传输；这是工程建议，不是 Owlbear 提供的云端房间 API。[WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)

## 部署及推进顺序

1. 先取得现有角色卡后端当前源码 / 部署说明，核对真实 schema 与货币、资源等差异；从插件真实夹具建立映射测试。无需改当前线上数据。
2. 做最小完整闭环：一个角色、一个棋子，HP / 临时 HP / 专注，包含授权、双向编辑、回执、断线重连和并发消耗。直接选择服务桥接，避免做完标签页专用方案后再推倒。
3. 扩展至状态 / 法术位 / 资源 / 背包，以及完整角色字段的适配，再做兼职、变身、多个场景及多个玩家。
4. 部署一个 HTTPS/WSS 服务与持久数据库，配置反向代理升级连接、允许的网页来源、备份及健康检查。头像独立文件或对象存储。可部署在现有主机，不要求先购买新机器；实际资源需求在多人样本上测量。GitHub Pages 可以继续托管前端，同步服务另设地址。
5. 自部署和官方托管使用同一协议，托管账号 / 配额与角色规则分离，后续 C++ WebView 客户端也复用该协议。

必须真实双端验收：玩家网页改 HP 后 DM 场景更新；DM 场景改状态后玩家网页更新；并发扣血不丢；重复消息不重复消耗；离线重连不覆写；刷新 / 切场景 / 删除棋子 / 重新绑定不会串人；升级与换装备不补满 HP；无关玩家不能读取或修改私人角色；第三方气泡兼容边界明确。未通过这些测试，不称“已实现双向同步”。
