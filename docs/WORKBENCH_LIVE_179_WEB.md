## 已验证的消息边界

新增 `tests/e2e/live-update-179.spec.ts`，使用两个真实同源浏览器窗口：宿主测试窗口通过 `Window.postMessage` 向真实 Full Suite App 发送消息。它覆盖真实窗口消息传递、`platform/workbench.ts`、React App 与角色纸卡，不运行完整 Owlbear SDK／服务器，因此不代表真实房间端到端延迟验收。

三个用例通过：

1. 角色卡保持当前页、没有本地编辑时，第一次远端状态增加／移除与生命值修改均应用到当前卡，不需要切换角色。测试刻意保持 `dnd_card_web.revision` 不变，只提高 `_suiteRevision` 并改变正文；本地编辑计数器不会阻止这种更新。
2. 只发送新 `catalog` 时，上方角色标签可以更新，但当前角色正文、生命值和状态继续保持原文档。随后发送包含新文档的 `selection`，当前卡就会应用更新。总览条目不是当前角色文档的替代物。
3. 延迟到达的较旧持久化修订不能让状态复活。相同目标的更高持久化修订，即使传输 `sequence` 比之前更低，仍可刷新当前内容。

这将“没有及时发出新文档”与“前端丢掉已收到的新文档”区分开。本次没有复现无本地修改时 App 丢掉有效 fresh selection 的问题。尚未排除其他负载、断线或权限组合；不能由这些检查断言所有现场问题已解决。

## 接收与应用规则

- `acceptSnapshot` 使用宿主序号区分选中顺序，同时用 `_suiteRevision` 防止旧正文覆盖新正文。
- App 当前卡的应用签名包含完整目标、文档与仓库修订；签名变化且当前卡不 dirty 时重新应用远端文档。
- 有 `dnd_card_web` 时，App 以原生文档的状态、资源和生命值为准，不再把另一个迟到的场景投影强行盖回正文。
- dirty／结果未确认保护仍有必要：本地修改尚未收到终态时，不用旧快照回退用户输入。本轮未删除这些保护。

宿主读取链路检查发现：普通 `loadCard` 有缓存就返回；远端通知只使缓存时间过期；全房间 `hydrate` 原先串行检查所有卡，正在执行时新增调用直接返回。因此需要宿主及时为发生变化的当前卡取得 fresh document 并发出 selection，而不是让前端把 catalog 当成完整文档。该宿主问题及其修复结果应以宿主的专门测试为准。

## 增量保存的实际范围

不能把当前实现描述成“每次保存整张卡”，也不能描述成“所有不变正文都永不发送”。

- Web 已有带 `dnd_card_web` 的观察基线时，`save` 使用 `documentChanges` 生成 native 和 legacy 两组差异；对象递归到变化叶子。因此单独修改生命值等数值时，不会顺带上传未变的头像、规则包和大段正文。
- `documentChanges` 把数组当作一个叶子。改变 `selections`，例如只加一个状态，仍会携带整组 `selections` 的 before、after、observed。已学法术等条目的正文如果在该数组内，也会随这一个变更数组发送。这不包括整张角色卡的其他不变字段。
- 还没有原生观察基线的兼容路径保留全量输入，供旧角色格式首次保存使用。
- 宿主用最新原文档重建三方合并输入，保留既有冲突处理；向持久化服务写入时再次计算变化字段。数组在这一层仍是完整数组叶子。
- relay 超过 4 KB 的传输会 gzip；本地直连使用浏览器 `postMessage`，不走 relay 的压缩函数。

没有把数组改成位置索引增量；角色条目的排序、删除及 ID 合并不能直接用数组下标代替。

## 无需新协议的有限瘦身候选

当前 Web 已支持：同一目标的 selection 没有 `document` 时，保留已收到的文档。因此宿主理论上可在“同一客户端、同一当前目标、正文完全未变”时省略重复正文，只发送目标状态。

这只能用于目标信息变化但正文未变的场景。重连、换卡和首次载入仍须提供完整文档；旧资料可能正文改变而 `_suiteRevision` 未改变，不能仅凭修订号相同就省略。此建议本轮没有实施，不改变协议或验收口径。

## 保存 ACK 边界检查

完整宿主模拟的第三轮在重新拖入自定义状态后出现过一次 5 秒观察超时：本地已有气泡且显示正在同步，测试文档尚未出现该状态，没有浏览器异常。前两轮和后续一轮该步骤通过。此单次失败不能因为重跑通过就视为不存在，也不足以判定 Web 丢失保存唤醒；现场 helper 已补上最近请求／ACK、宿主 metadata、场景 items 与 broadcasts 诊断，供再次发生时定位。

只读复查没有发现旧保存完成清理直接删除新任务的路径：每次修改独立更新 80 ms 批次计时器；计时器触发时先取走该批次，再进入每个角色的写入队列；队列和保存 flight 的 finally 都检查任务身份后才清理。App 为每次待保存操作计数，不靠下次渲染偶然触发保存。

新增 `tests/e2e/save-race-179.spec.ts`，通过真实 workbench 模块、窗口消息和 mutation queue 测试 20 组相邻修改，共 40 次写入。ACK 延迟分别为 0、25、79、81、120 ms，第二次修改安排在 ACK 前约 5 ms、同一时点或后约 5 ms。全部收到两次保存并得到最终数值，浏览器用例通过（7.2 秒）。该用例针对 Web 队列的清理边界，不包含完整宿主持久化服务，不能据此解释上述单次端到端超时。

另有一个未实施的观察项：批次记录的 `queuedAfter` 当前未使用。若前一 ACK 已完成清理、后一批次尚未触发，其捕获的 observed 基线可能较旧；这属于三方合并基线问题，不等于请求没有发出。本轮未证实它造成该状态问题，没有据此修改生产代码。
