## 复现

在前一提交 `4da0b4cd6f37d1c2ad6181baeee2864d25df50ac` 的生产 standalone 构建中，阻断首次 `cardRuntime-*.js`。数据库当前工作区的角色名为“当前已保存角色”，上一份备份为“已读取的旧备份”；二者笔记、修订、敏捷、临时生命及资源名称/当前值/上限均有区别。角色簿还包含另一名角色，独立 `recovery:unrelated` 记录含恢复草稿。

点击“导入 / 导出 → 读取上一次保存”后，页面确实显示旧备份；持久工作区仍为新版本。放开模块请求并点击“保存后重新加载编辑功能”后，编辑库恢复，但页面角色名回到新版本。新增回归实际失败在“期望已读取的旧备份，收到当前已保存角色”，证实父任务判断。原备份仍在，不是永久丢档。

最初测试夹具把 `abilities.dex` 当成对象，先发生夹具类型错误；修正为模型实际的数字后完成上述产品失败复现。这两次日志分别保留，没有把夹具错误当作产品证据。

## 修复与保存边界

- `acceptWorkspace(..., true)` 为两个现有备份读取入口标记“已接受但尚未保存”，状态栏明确显示“备份已读取，尚未保存”。正常启动读取不标记。
- 编辑库重试仅在此状态下调用原 `persist(workspaceRef.current)`。保存完整已接受工作区，沿原队列和 IndexedDB 原子事务提交；不从派生当前角色重建角色簿、不做远程角色写入、不调用或清空独立恢复草稿。
- 只有当前工作区的成功保存才清除此标记。普通编辑保存与现有同步副本成功保存保持状态一致。保存旧恢复版本成为当前工作区后，原新版本成为上一份备份，可回查。
- 保存失败、保存尚未结束或只读页都不重载；失败后内存恢复版本和导出入口保留，原持久工作区与备份未变，可重试。
- 重试进行中禁用按钮，并以同步 ref 阻止同一轮快速重复点击。普通重试不再次写盘，不轮换另一份有效备份。
- 已读取而未保存的备份加入原离页保护；用户取消离页时保留当前可见恢复版本，不自动提交。

已读取备份仍沿用原“读取完整工作区”的语义，本轮不把它改成合并当前角色或选择性恢复。独立远程恢复草稿属于不同记录，保持原样。
