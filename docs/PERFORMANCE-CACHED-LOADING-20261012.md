# 缓存重开与主线程处理检查点

按用户要求，以 10 张混合卡为测试底线，保留 1 张和 4 张复现。此次使用安装的 Chrome 154.0.8037.98、新建隔离环境、1440 × 960 视口和本机 HTTPS 资料服务。229 份公开资料逐一核对内容哈希，总正文约 52.3 MB；测试卡约 2.06 MB，包含空白卡、20 个法术的施法者和较大施法者，当前选中 20 个法术的施法者。未读取用户 Chrome 的资料或凭据。

## 已测到的现象

未开启 CPU 采样的一次 10 卡运行，初次准备资料约 23.8 秒，缓存重开约 10.9 秒。缓存重开记录 229 次缓存读取、232 个后台处理任务和 44 次主线程长任务；最大的一次怪物处理请求等待约 1.8 秒。后台等待包含排队和交付，不能直接视为后台 CPU 时间；并行读取的耗时不能相加后当成总加载时间。

主线程 CPU 采样中，资料缓存返回、后台消息交付、索引构建和重复技能查找均有可见开销。技能选项此前每次都会遍历整套资料，候选修正为先筛出当前版本的技能，再逐项匹配。每次生成选项都重新建立局部候选集合，保留已有选择优先、资料顺序和版本匹配规则。

相关 30 项回归通过、1 项既有检查跳过；新测试的必填字段修正后另有 2 项检查通过，类型检查通过。相同 CPU 采样条件下一组 10 卡对比，缓存重开约 11.28 → 11.00 秒，主线程长任务累计约 4.73 → 4.14 秒，最长一次约 158 → 202 毫秒。两轮各 20 次交互无失败。这是单组诊断数据，不能据此声称整体性能达标或 P95 已改善。

## 未采用的尝试

完整归一化对象缓存没有加速，已撤回。分块消息改用另一种交付等待方式，一组对比中仅缩短约半秒，主线程长任务却从 44 次增加到 64 次，累计时长也增加；暂不采用，源代码已恢复。两个尝试均未发布。

技能查找候选曾有一次测试误用旧构建，已取消并标为无效；有效结果单独使用 `choice-lookup-corrected` 文件名，保留构建及测试源文件指纹。
