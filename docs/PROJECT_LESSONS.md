# Full Suite 项目经验与故障复盘

截至 2026-09-24 / 发布 193。入口与版本证据见 [AI_HANDOFF.md](AI_HANDOFF.md)。本文提炼已证实的原因与可复用的验证方法；不是把历次用户愿望都标记为已完成。

## 1. 同步不是一个“网络慢”问题

本项目出现过 UI 意图丢失、SDK 消息往返过多、Proxy 拷贝异常、读写不同文档、HTTP 缓存过时、持久提交后的投影阻塞等不同根因。替换窗口类型或笼统重写协议不能同时解决这些问题。先回答：谁拥有数据、请求什么时候算成功、哪一步开始等待、旧消息怎么被拒绝。

现有分层是：界面乐观草稿 → 明确操作意图/增量 → 宿主权限及三方合并 → 持久文档或库存事务提交 → ACK 与通知 → 棋子投影/其他客户端更新。怪物 metadata 本身就是持久层，不能省略等待。投影不是第二个可以随意覆盖人物文档的权威。

### 1.1 SDK Proxy 无法 structuredClone

- 症状：修改 HP、资源或保存卡报 `DataCloneError`，堆栈包含 `Array.map`、`Immer produce`，有时已持久写入却在投影时报错。
- 根因：SDK `updateItems` 回调参数是 Immer Proxy；直接 `structuredClone` 不支持它。曾用纯普通对象的 mock，导致测试漏掉真实边界。
- 修复：Suite `src/workbench/clone-json.ts` 逐值构造普通 JSON 容器，metadata/合并快照走此边界。普通已序列化文档仍可用 structuredClone，不要全仓盲换。
- 回归：`node tools/workbench-proxy-178-selftest.mjs`，真实安装的 SDK callback 与嵌套资源。详情 `docs/WORKBENCH_PROXY_178.md`（Suite）。

### 1.2 自动生成时间戳误判业务冲突

- 症状：保存被 `owlbear.meta.parsed_at` 拒绝，用户没有编辑这个字段。
- 根因：增量投影合并没有沿用完整合并对生成元数据的精确路径规则。
- 修复：只对明确的 bookkeeping 路径采用相应归并规则，时间戳取有效较新值、native revision 不倒退、宿主 revision 不接受客户端指定。
- 不可做：全局忽略所有叫 revision/updatedAt 的字段；规则/资源内部同名字段仍然是业务数据，应严格检查冲突。

### 1.3 旧状态/资源复活与切卡后才刷新

- 症状：几分钟前删除的状态回来，远端姓名/职业/法术不更新，切离再切回才看到。
- 确认的不同原因：旧棋子投影被当作新编辑；广播/快照版本倒退；旧卡跨房间后仍从原上传地址读，却向当前房间写；相同 mtime/长度导致重复 ETag/304。
- 修复位置：`runtime-authority.ts` 的 baseline 与 documentRevision；`card-location.ts` 统一读/CAS/回读/删除位置；文档失效读取和较新 revision 处理。
- 核心约束：原上传房间的文档地址与当前场景库存作用域可以不同，不能把两者混为一谈。未知更新结果需要终态回执或明确对账，不能超时就盲重放。
- 回归：Suite `workbench-document-181-selftest.mjs`、`workbench-host-181-selftest.mjs`、`workbench-live-179-cache-probe.mjs`；Web `live-update-179.spec.ts`、`sync-order-176.spec.ts`。细节看 Suite `WORKBENCH_SYNC_181.md`。

### 1.4 第二次连续操作没有通知，随后回弹

此症状至少有四层原因，不能修一层就宣布全部解决：

1. **客户端意图丢失**：`5 → 4 → 5` 的第二次目标 5 与旧已确认值 5 相减得到空差量，排队执行时实际值已是 4。按钮必须提交“把 current 设为 5”的字段意图，在执行时合并最新资源；配置编辑才按其编辑基线计算差异。
2. **控件结束时吞了新 props**：等待 ACK 时远端又更新，控件仍只保留旧乐观值。需验证 ACK、props 更新与 loading 清理的先后，不能只读最终一次 render。覆盖见 Web `control-settlement182.spec.ts`。
3. **宿主 ACK 被提交后工作堵住**：持久文档已写，却等 token SDK 投影或通知广播回应，第二笔卡在队列。人物投影改为每卡串行、合并到最新已提交版本；通知不等待远端广播 ACK。怪物仍等 metadata 实写。
4. **每笔强制重新 GET 整卡**：已有刚提交的有效权威缓存，却每次 `read(a,true)`，被慢网络再次拖住。183 使用有效缓存、远端事件失效，保留服务器 SHA/CAS；不是取消并发保护。

回归要求：真实控件 `2 → 1 → 2 → 0`，跨 80 ms 保存批次、延迟/乱序 ACK、另一玩家改上限、两个资源交错、撤销重做、法术位三份表示一致；捕获实际发出请求和逐帧界面，不能只断言最后恢复正确。Suite 用生产 background + 实 SDK iframe，故意扣住投影/广播回应和延迟 GET。

代码/证据：Web `resources.ts`、`mutationQueue.ts`、`resource-burst182.spec.ts`、`save-race-179.spec.ts`、[客户端复盘](RESOURCE_BURST_182.md)；Suite `WORKBENCH_RESOURCE_182.md`、`WORKBENCH_RESOURCE_183.md` 及同名 selftest。

### 1.5 选中卡片、投骰为什么也会卡

- 178 检查安装的 SDK 后发现 getters 不缓存；`getItems(predicate)` 在插件侧过滤，仍取得整场景。多次 catalog/hydrate/selection 组合形成大量重复的 SDK 往返。
- 修复使用事件更新的 observation 快照、按 ID 请求、独立读取与选择代次检查；权限变化必须立即失效缓存，慢 A 卡读完不能抢回已切到的 B 卡。
- 一项实 SDK 受控夹具中，旧版切卡有 25 次请求、4 次整场景响应；这证明重复工作存在，不代表实际用户网络固定有某个延迟。
- 别把用户“同时启用旧插件反而快”当解决方案，也别把弹窗比标签页快当结论。需要比较真实请求/事件路径。
- 证据：Suite `WORKBENCH_SDK_PROFILE_178.md`、`WORKBENCH_TRANSPORT_178.md`。窗口引用丢失时保留中继回退，不能假定右键拆分、复制链接和左键启动拥有相同 opener。

### 1.6 背包“已转移/被其他人修改”和状态无法移除

- 状态与库存授予不能混用同一种条目身份；普通状态添加不能凭空制造背包行。无关数值编辑不应强制访问库存 ledger。
- UI hydration 补出的状态注解/空对象与原始 observed 快照不同，不能把它们当远端编辑冲突。`documentChanges` 必须区分 observed 缺失、null 和已有对象。
- 格位移动依据手势开始时 `observedSlots` 做三方判断；无关资源/数量更新不能仅因容器 revision 改变就拒绝移动。真正的同物品争用、占位、权限变化继续拒绝。
- 权威库存 positions 必须写入 native 文档并参与投影确认；只切卡不能恢复旧位置。操作 ID/回执幂等、跨容器转移原子性不能为“不卡”而省略。
- 回归：Suite `inventory-model-selftest.mjs`、`workbench-inventory-sync-selftest.mjs`、`workbench-inventory-178-selftest.mjs`；Web `inventory-race181.spec.ts`、`inventory-queue-181.spec.ts`。

### 1.7 React #31 白屏：对象进入数值 UI

旧角色货币有 `inventory.currency.wallet`、平面 currency 与 native coins 等结构。把 `{gp,pp,ep,sp,cp}` 整对象传给 React 数字文本会崩溃。Suite `currency.ts` 先归一成五个有限数值；首建库存保留旧卡实际金额。回归必须含旧格式，不能只用新建空卡。

## 2. 导入与计算的经验

**成功提示必须对应产品真正的数据入口。** 192 中本地 persist 成功却不代表枭熊角色簿增加。导入应先验证，再由当前模式选择本地保存或房间 createCard，等正确提交后显示成功。单机通过不能代替枭熊通过；要覆盖无棋子、玩家权限、拒绝、断线与重复点击。

**调整值与最终值不能混用。** 193 AC = 规则/旧绝对基值 + 手动 offset。若场景传入最终 AC 18 且 offset 3，应存基值 15，而非基值 18 再显示 21。同类字段变化要同时检索 engine、UI、validation、export、旧格式导入、宿主 runtime 投影与撤销，而不是只加一个输入框。

**角色权威与投影必须都能验证。** native/legacy 双增量测试要分别应用实际补丁；不能总是从 native 重新导出 legacy 后宣称双向正确，否则会掩盖 legacy 补丁漏字段。

**自动资源不能在读取/刷新时发放两次。** 种族速度可从结构读取；背景加点、装备同调与快捷引用各有不同语义。空卡、旧卡、升级、多职业、手动修正、撤销/重做都应保留既有消耗。

## 3. 资料库、作用域与 UI 的经验

- 来源配置不等于角色基础版本。191 后本机网站 `siteSources` 共用，但各卡 2014/2024 与 Wiki 版本筛选不变。联机使用 DM 共享规则，不把本机配置覆盖到房间。
- 默认全扩展只适用于新默认/尚未手动处理来源。迁移沿用当前角色来源并留旧快照；新建、导入、刷新不能悄悄重开手动关闭项。撤销角色编辑不能顺带还原旧全站配置。
- 未开启来源应完全隐藏；开启来源内单项禁用是保留并划线。这两个概念曾被混为一种 disabled。
- 大列表先完整排序再窗口化渲染；不要只排序已加载可见子集。全局搜索状态只有一份且不应更改各分类列表筛选。
- 目录/表格/tooltip 的滚轮归属需要显式验证；手机滚动不能因 pointerdown 就选中或开拖拽。长按阈值和 pointercancel 要走完整清理。
- 在 A4 缩放内测量拖拽偏移、头像位置、切角裁剪时，区分 CSS 逻辑尺寸与屏幕包围盒。图标使用等比缩放，不能先假定是 DPI；100% 缩放也可能出现可用高度不足。
- 调色等高频操作先更新局部视觉，确认时再写角色/历史，避免每个 input 事件引发整卡同步。
- 布局被 toast/重连文本撑开、恢复提示改变高度，属于真实功能缺陷；错误需可复制诊断，但不应反复改变卡片几何。
- 页面预览的布局测试与真实玩法验收分开。DOM 没溢出不能证明用户看得清，受控拖拽通过也不能证明实体平板触感合格。

## 4. 发布与协作的经验

**不要从脏主目录生成线上包。** 这里主目录落后于线上提交，但工作文件有回填和实验并存。193 的正确方式是从已发基线建立隔离源码，做最小补丁、测试、提交，生成与提交一致的源码 ZIP，再精确回填主目录。禁止一键覆盖、reset/clean 或把全部未跟踪内容 add 进去。

**源码与产物要成对。** 普通 Web build 供 Suite；standalone build 在构建图排除联机。Suite 构建环境变量指错 Web 目录会静默打进实验。源码下载、manifest、前端 hash 和宿主版本应有回执；192 是只换前端的热修复，不能假设每次 Web 修改都改过宿主 manifest。

**旧标签页需要旧 hash 资源。** 暂存新包、校验、备份切换；保留旧 hashed assets，避免在线用户切页时 404。单机下载旧版本不要随新包无意删除。中继、稳定版、nginx 与角色数据明确记录是否改动。

**已有脚本是范本，不是永远可重复执行的安装器。** 193 部署脚本守卫旧版本与备份不存在，二次运行理应失败。换版本时逐项核对源提交、目标路径、归档名、旧版本断言与回滚目录，不能粗暴替换所有数字。Windows 文件操作使用同一 shell 与 LiteralPath，先确认递归目标。

**不要把记录旧状态当作现状。** `STATUS.md` 是流水；Suite 的 `NEXT_SESSION_HANDOFF.md` 是历史三龙牌工作，不是 Full Suite 工作台总交接。旧文档里的“浏览器工具不可用”“未部署”只适用于当时，需用当前证据复核。本次交接文档没有自动把旧模块待办标记完成。

**构建脚本会在换 shell 后静默失败。** Suite 的 `tools/build-workbench-dev.mjs` 用 `execFileSync('tar',…)` 打包 `source.zip` 与 `suite-source.zip`；在 Git Bash 里 `tar` 解析到 GNU tar，会把盘符路径当成远端主机，报 `Cannot connect to F: resolve failed`，整个 tar 步骤直接失败。195 发现上一次构建正是如此：`dist-workbench-dev` 已生成、两个 source 包却不存在，肉眼很容易当成构建成功。换到 PowerShell 运行，或把 bsdtar 目录放在 PATH 前面即可。打包脚本的断言只覆盖文件哈希与版本号，不覆盖 source 包是否存在，正式发布前应显式确认这两个文件非空。

**许可与用户范围都是发布边界。** 必须保留对应源码及专用非商用许可，不把它描述为 AGPL。用户曾授权稳定版公告，不代表每次测试版修复都要重发稳定版。本次仅记录文档，不触发构建/推送/部署。

## 5. 再收到“同步慢/回弹”时的最短诊断路线

1. 确认双方实际加载的 manifest/JS hash、是单机还是带会话的 workbench、当前 direct 或 relay、角色原始文档地址与绑定棋子 ID。
2. 从可复制报错取 `requestId`、type、phase、文档 revision、expected/observed；为一条操作记录“点击 → 发送 → 持久提交 → ACK → token 投影 → 另一端显示”。不要只量 toast 出现时间。
3. 分别测试首次与连续 `A → B → A`，并在另一客户端始终停留当前卡；加一次远端独立字段修改、一次真同字段冲突。
4. 确认请求内容保留最终用户意图，旧 ACK/catalog/selection 没覆盖草稿，队列 finally 没漏唤醒；再查宿主缓存/SDK 往返和持久后的等待。
5. 人为扣留某个边界回应，运行真实控件/实际宿主代码；测试夹具不能替被测层重新计算正确结果。失败旧版本与修复版用同一夹具对比。
6. 只在已提交时通知；不可见角色的通知需裁剪隐私。变更只发生一次、音效只播一次，投影 echo 不再触发动画/通知。
7. 报告中分别写“代码根因已复现”“本地/线上模拟通过”“真实用户房间是否确认”。用户仍复现时保留其失败结论，继续收集新的时间线。

## 6. 后续交接文档的更新格式

每次实质修复记录：用户原症状；可复现根因与排除假设；最终改动文件；失败前/修复后同条件证据；已测和未测边界；两个源码提交；实际发布端与版本；回滚位置；未纳入内容。新的用户验收意见单独标注，不用后来的一次构建成功覆盖历史失败。

## 2026-09-27 起始装备格式回归：数组方法与同名资料字段

上游背景的 startingEquipment 是数组，职业则可能是含 entries/default/defaultData 的对象。先读 equipment.entries 会取到数组原型的 entries() 方法，进而在 blocks.map 崩溃，连带整个资料文件被判失败。应先 Array.isArray，再从对象中读取并验证字段类型。新增格式不能只测新增职业夹具，必须带上原有背景数组、空数组、同文件其他类别以及真实文件；缓存里保存的是有效原始 JSON，代码错不能靠重试或删用户数据解决。本轮补10份真实文件及生产后台/回退、重试和缓存恢复证据，原始上游快照仅存仓库外。

## 2026-09-27 交互回归与公告前置

增加首次公告、统一导入入口和普通/编辑模式分工后，旧用例要按用户确定的行为更新，不能反改产品只为旧断言通过。公告用例单独覆盖强制确认，其他用例显式预置确认。键盘聚焦正文引用会触发浏览器自动滚动；scroll 统一关闭提示会吞掉刚产生的 onFocus，应保留当前键盘聚焦且可见的提示并更新位置。真实上游无解析异常不等于真实全库速度已经验收。
